## 1. What this plan decides

Every first-party measure already carries `event_id`. The spine keys therefore live on `events`, computed by the server, and each measure reaches them by joining through `event_id`. No measure table gets a new column. This keeps never-who intact: every key describes a place, an event or a day, never a person.

The spine (ADR-010 in OCR-docs, status Proposed):

```
corridor  ->  venue  ->  event type  ->  event
H3 res-7      venue_canonical_id   uec_code    event_correlation_id
```

| Key                    | Grain                                             | Exists today?                | Where it lives                                                             |
| ---------------------- | ------------------------------------------------- | ---------------------------- | -------------------------------------------------------------------------- |
| `brand_id`             | tenant (venue operator, league, chamber, sponsor) | yes                          | `events.brand_id`; tenant tree in `node_hierarchy`                         |
| `corridor_id`          | an area, the H3 res-7 cell                        | yes, with a caveat (see 1.1) | `events.h3_res7`; `events.corridor_id` is a legacy slug                    |
| `uec_code`             | event type                                        | yes                          | joined from the type registry at export time (`event_type_id` on `events`) |
| `venue_canonical_id`   | one physical venue                                | yes, since migration 0104    | `events.venue_canonical_id`, computed by the server (OSE-1615)             |
| `event_correlation_id` | one event: this venue, this type, this night      | yes, since migration 0104    | `events.event_correlation_id`, computed by the server (OSE-1615)           |

### 1.1 What "corridor id" means in code

A corridor is a res-7 H3 cell, never a slug. `canonicalCorridorId(r.h3_res7 ?? r.corridor_id)` (`handlers/bigquery.ts:156`, `lib/export-geography.ts:78`) writes the lower-cased cell, or `'unknown'` when the value is not a valid cell. `assertCorridorGrainRow` throws on anything finer than res-7. The old slug in `events.corridor_id` (migration 0029) is only a fallback for events geocoded before the cell columns existed (`COALESCE(h3_res7, corridor_id)` in `refreshCorridorBaselines`). New work reads `h3_res7`.

Notes the table cannot hold:

- **`registration` and `survey` were missing from the 2026-10-04 audit and from the first version of this plan** (found by the 2026-10-05 re-check). Both are written by the form handlers, carry `event_id`, and set the `ose_anon` cookie (section 3). They bring the count to nine measures. OSE-1616's registry must declare them, and their privacy classes need the same sign-off as the rest. `subscribers` (`handlers/pages.ts:2448`, the landing-page signup, no `event_id`) is a tenth writer outside the event spine; it is listed here so it is not found by surprise, and is not classed as a measure.
- **`FORMS_DB` rows never join to `DB` in SQL** (ADR-001). A roll-up that needs `checkin` or `email_signup` by corridor reads `events` first, then counts per event in `FORMS_DB`. `handlers/dashboards.ts` is the one authorised reader (`tests/architecture.spec.ts`).
- **The two scan rows share no durable key** (OSE-798). The placement row answers "how many, where"; the node-return row answers "did this browser come back". Neither is joined to the other.
- **Derived tables** (`scan_aggregates`, `scan_cell_aggregates`, `anon_id_returns`, `corridor_density_snapshots`) are materializers over the above. They carry `h3_res7` (and `event_id` where the grain allows), so they inherit the spine through the same join. They are not measures.

## 3. Where `ose_anon` is set

The `ose_anon` cookie (HttpOnly, Secure, SameSite=Lax, one year, `lib/anonymous-id.ts`) is set in exactly two places:

- the QR scan path, `/q/` (`handlers/qr-scan.ts:215`);
- the form paths: register, check-in, survey and email signup (`handlers/forms.ts:304, 423, 470, 526, 555`).

Public read surfaces set **no cookie**: the landing page, `/events`, the event page, the display, the poster, the map and the shortlink redirect (OSE-1312). So "a visitor gets a cookie" is true only for a person who scans a printed code or submits a form. A person who only reads a page, or follows a short link, is counted (a day counter, a card impression) but never marked.

## 4. Decisions

### Decision 1: the time bucket in `event_correlation_id` (DECIDED, PO 2026-10-04)

ADR-010 defines `event_correlation_id = hash(venue + uec_code + time_bucket)`. The bucket has to keep one league night as one id, and keep two different nights apart.

| Option                                                                                       | A league night that runs past midnight                                 | Two leagues, same venue, same type, Tuesday and Thursday | Verdict    |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------- | ---------- |
| Calendar day, UTC                                                                            | splits when UTC midnight falls mid-event (any evening event in the US) | kept apart                                               | no         |
| Calendar day, event local time                                                               | splits if the event crosses local midnight                             | kept apart                                               | close      |
| **Local day with a 04:00 rollover** (a start before 04:00 local belongs to the previous day) | stays one night                                                        | kept apart                                               | **chosen** |
| ISO week                                                                                     | one id                                                                 | **merged**, wrong                                        | no         |

Decision: **the local date of `starts_at` in the event's own IANA zone, minus one day when the local start time is before 04:00.** Written `YYYY-MM-DD`. The rule works on the wall clock, not on a subtraction of 4 hours from the instant, because the two disagree by an hour on a daylight-saving day and OSE and OW must compute the same id. `starts_at` and the zone already exist (OSE-1313); `zonedDatePart` and `zonedTimePart` in `lib/event-datetime.ts` give the local date and time. A date-only event (no `starts_at`) uses `start_date`. The id is recomputed when the start changes, so adding a start time to a date-only event can move its bucket. The hash input is versioned (`v1`), so a later change to the rule is visible rather than silent.

Test vectors (zone `America/Chicago`), the cases OSE-1615 must pass and OW should run too:

| Start (UTC)            | Local start                       | Bucket       |
| ---------------------- | --------------------------------- | ------------ |
| `2026-10-22T23:30:00Z` | Oct 22, 18:30                     | `2026-10-22` |
| `2026-10-23T06:30:00Z` | Oct 23, 01:30 (a late night)      | `2026-10-22` |
| `2026-10-23T09:00:00Z` | Oct 23, 04:00 (exactly the edge)  | `2026-10-23` |
| `2026-11-01T09:30:00Z` | Nov 1, 03:30 (fall-back day)      | `2026-10-31` |
| `2026-11-01T10:30:00Z` | Nov 1, 04:30 (fall-back day)      | `2026-11-01` |
| `2026-03-08T09:30:00Z` | Mar 8, 04:30 (spring-forward day) | `2026-03-08` |

Known limit, accepted: two separate sessions of the same type at the same venue on the same night (a 7pm and a 10pm trivia) share one id. They are one night to a league or a chamber; if a buyer needs them apart, the bucket gains a session part in `v2`.

### Decision 2: where `venue_canonical_id` lives (DECIDED, PO 2026-10-04)

Today there is no canonical venue entity. An event carries free text (`location` and `where_address`), `lat`/`lon`, and the cells `h3_res9` / `h3_res7`.

Decision: **a new nullable column on `events`, computed by the server, not a new venue table.** It is `hash('v1' + normalised venue name (`location`) + h3_res7)`. Normalisation lower-cases, strips punctuation and leading "the", and collapses whitespace. No coordinates enter the hash. This is what OSE-1615 already assumes, and it avoids building a venue registry before there is a second consumer that needs one.

Known weakness, accepted for now: the same venue geocoded into two neighbouring res-7 cells gets two ids, and two same-named venues in one cell share one. Both are rare at the current scale and are visible in the data. If either shows up, the fix is a registry, and the column becomes its foreign key.

**Missing inputs mean no key.** `venue_canonical_id` is null when the event has no `location` or no `h3_res7`. `event_correlation_id` is null when `venue_canonical_id`, the event type (`event_type_id`, which gives `uec_code` through the type registry) or the start date is missing. A key is never computed from part of its inputs, so an untyped event never joins an `unknown` bucket with other untyped events. (Exports today write `uec_code` as `'unknown'` for such rows, `handlers/bigquery.ts:158-159`; the key stays null.)

Per ADR-010 the normalisation is a shared contract between OSE and OW, so "hash" and "normalise" must be exact. Until 2026-10-12 this plan listed the exact rule as "proposed defaults". OSE-1615 pinned and published it that day as **version `v1`**, with fixtures (names in, id out) the OW side can run. **What the PO decided** is Decision 1 (the night) and the paragraphs of Decision 2 above (a column on `events`; a hash of `v1`, the normalised venue name and the res-7 cell; lower-case, punctuation stripped, a leading "the" dropped, whitespace collapsed; no coordinates), and the apostrophe ruling below. **Everything else in this list was proposed in this plan on 2026-10-04 or chosen by the builder on 2026-10-12, and is for the PO to confirm.**

- **Normalised name**, in this order: remove apostrophes; Unicode NFKC; lower-case (the Unicode lower-case mapping, not case folding), then NFC; remove apostrophes again; remove variation selectors, enclosing marks and characters that are not seen (a soft hyphen, a zero-width space or joiner); `&` becomes `and`; every other character that is not a letter, a combining mark or a digit becomes a space; a combining mark with no letter or digit before it is removed; a leading `the ` is dropped; runs of spaces collapse to one and the ends are trimmed. ("Joe's Tavern" and "Joes Tavern" agree; "Tom & Jerry's" and "Tom and Jerrys" agree; "St." and "Street" do not, and that is accepted.) The PO decided lower-case, punctuation stripped, a leading "the" dropped and whitespace collapsed. NFKC and `&` to `and` were proposed on 2026-10-04. The order of the steps, NFC, the apostrophe set, and what happens to marks and unseen characters are the builder's.
  - **PO, 2026-10-12, on the apostrophe.** Two messages, in order, verbatim with their typos: first "I would think the Apostrophe would need to be supported to maintain reality", then "it this is a technical issue, remove. if this about text display type for end use display, keep." The second is conditional, and **the builder made the classification**: comparing two venue names inside the hash is treated as the technical case, so the apostrophe is removed there; `events.location`, which every page shows, is the display case, so the name is kept exactly as typed. Test: "an apostrophe is kept in the name as typed, and ignored only when comparing venues" in `tests/spine-keys-store.spec.ts`. If the PO meant the apostrophe to count when comparing, so that "Joe's" and "Joes" are two venues, the PO has to say what it becomes: kept as a character, or a space ("joe s"). Either is the two apostrophe lines in `lib/spine-keys.ts` and new fixtures, at the cost described under "What a later change to the rule costs". **Confirmed by the PO, 2026-10-13.** Asked which of the builder's choices to confirm as built, from a list of four, the PO chose this one, worded: "Comparing venues is the \"technical\" case: Joe's and Joes are one venue, and the name is always shown as typed." The PO did not choose the other three (venue corrections, accents kept apart, the other defaults), so they remain the builder's.
  - **Builder's choice:** which characters count as an apostrophe: `'` (U+0027), `’` (U+2019, what a phone types), `‘` (U+2018), `ʼ` (U+02BC), the backtick and `´` (U+00B4), plus the full-width `＇` (U+FF07) through NFKC.
  - **Builder's choice:** a combining mark stays with its letter. The 2026-10-04 wording said "every character that is not a letter or digit becomes a space". Taken literally that turns the vowel signs of Thai and Devanagari into spaces and merges different names (found in review, 2026-10-12). Marks that belong to no letter (the selector after an emoji, a keycap) are removed, so "🏟️ Eagles Hall" is "Eagles Hall".
  - **Not folded, and that splits venues:** accents ("Café Olé" and "Cafe Ole" are two venues), abbreviations ("V.F.W." and "VFW"), a suffix ("Joe's" and "Joe's Tavern"), and **a city or address typed after the name** ("Eagles Hall, Blue Island" and "Eagles Hall" are two venues). See "Open for the PO" below.
- **Hash (proposed 2026-10-04, pinned by the builder):** SHA-256 over the UTF-8 bytes of the joined string, fields separated by `|`, written as the first 32 lower-case hex characters. Venue: `v1|<normalised name>|<res-7 cell, trimmed, lower case>`. Event: `v1|<venue_canonical_id>|<uec_code, trimmed>|<bucket>`.
- **No secret key (proposed 2026-10-04, pinned by the builder).** OSE and OW must agree without sharing a secret (section 6 gives the consequence).
- **Bucket (PO, Decision 1):** the local date of `starts_at` in the event's own zone, read from the wall clock; a local start before 04:00 belongs to the day before. It is not "the instant minus four hours": the two differ by an hour on a daylight-saving day. A date-only event uses `start_date`.
  - **Builder's default:** a timed event whose zone is missing or unknown is read in `America/Chicago`, the platform home zone. "Unknown" means the runtime's time-zone database does not have it; OSE only stores a zone its runtime accepted.
  - **Builder's default:** only the first night is used. `end_date` is not read, so every measure of a three-day event carries the first night.
  - **Builder's default:** a `start_date` that is not a real calendar date gives no bucket.
  - **Builder's default:** `starts_at` counts only when it is written as an instant with its zone (`Z` or an offset). OSE always stores it that way. A string with no zone would be read in the machine's own zone, so it is treated as no `starts_at`, and `start_date` is used.
- **Type code:** `uec_code` as stored in the type registry, trimmed, case kept. **Builder's default:** an empty code or `unknown` (in any case) gives no key, so untyped events are never grouped together (the plan's own rule above; the casing and trimming are the builder's).
- **Where it is:** the rule is `workers/oursharedevents/src/lib/spine-keys.ts` (pure functions, no coordinate is a parameter). The fixtures are `workers/oursharedevents/tests/fixtures/spine-keys.v1.json`: venue names in several scripts, the six bucket vectors of Decision 1 and the zone cases, events, and the cases that give no key. The file states the rule in words, step by step, and the Unicode version it was generated with. Its hashes were computed with `node:crypto`, not with the library. In review on 2026-10-12, two implementations written only from those words, one in Node and one in Python on an older Unicode version, reproduced all 84 rows the file then had. The rows and steps added after that review (unseen characters, NFC, the instant rule) have been checked against this repository's function only.

**The event key is one night, not a series.** It is one venue, one type, one night (Decision 1). OSE-1692, written later, describes `event_correlation_id` as "a stable id tying the instances of one recurring event or series together, so a weekly night is one thing across a season". The build follows Decision 1, not that sentence: with the venue inside the hash, a weekly night gives a different id every week. Joining a season is the roll-up of section 5 (`brand_id`, `uec_code` and dates), or a later key.

**How the stored keys stay true to the row** (`src/lib/spine-keys-store.ts`). The mechanism is the builder's; OSE-1615 asked for "a backfill in the migration or a one-off admin job".

1. Every statement in the Worker that changes an input (`location`, `h3_res7`, `event_type_id`, `start_date`, `timezone`, `starts_at`) sets both keys to NULL in that same statement.
2. After the save, the server reads the stored row and writes both keys. The write lands only on the row it read.
3. Every night, once every other nightly job has settled, `runSpineKeyCheck` reads events of every brand, computes both keys again and writes them where they differ from what is stored. One run reads at most 5,000 events and writes at most 200 keys, and stops if it has run for 10 seconds; it starts at a point that moves each day, so a run that stops early does not stop at the same rows the next night. A row that cannot have a key costs no write. If another nightly job never settles, the check does not run that night and logs nothing.

What this guarantees: after a save through the Worker, a key is absent or right. What it does not: a writer outside the Worker (a seed file, a migration, a changed type code in the registry, SQL run by hand, an older Worker version running after migration 0104) can leave a key that no longer matches its row. Step 3 replaces such a key on its next run when fewer than 200 rows are waiting and the table has at most 5,000 events; otherwise over as many nights as that takes (in review: up to 5 nights at 10,000 events, 34 at 50,000). Within each page of 500 rows a wrong key is written before a missing one; across pages it is not, so right after a deploy, when many rows are missing keys, a wrong key can wait behind them. Until then the key can be wrong. The run logs `SPINE_KEY_CHECK` with its counts, at warning level when it corrected a key, met an error or stopped early; no alert reads that line (the repo has no alerting, OSE-1603), so someone has to look. Nothing reads the keys yet; the first reader (OSE-1617) must not assume a key is right on the day of an outside write.

Considered and not done here: a database trigger that clears the keys whenever an input changes would make step 1 hold for every writer at once. The deploy gate refuses any trigger (`scripts/verify-d1-canonical-shape.mjs`), and the test harness splits migrations on semicolons, so adding one is its own change with its own decision.

**A venue that is corrected gets the key of the corrected venue (builder's choice, for the PO to confirm).** OSE-1692 asked for this to be a recorded decision; this is the builder's answer, recorded so it can be confirmed or changed. The keys follow the row; no earlier key is kept, and measures joined through `event_id` move with it. The cost: there is no record that an old key and a new key were the same place, so a venue renamed between seasons does not join year over year by this key. That works against OSE-1692's aim that "year-two data joins to year-one". The alternative is a table of old key to new key, written when a venue's text changes.

**Rows saved before migration 0104 may be keyed less well than later ones.** Their venue text was typed before anything depended on it. They get keys from the nightly check over the nights after the deploy (200 a night), not at once. A past event with no map cell is never looked up again (the nightly place lookup skips events that are over), so it keeps no key.

A create or update that names either key is refused (400 `SERVER_COMPUTED_FIELD`).

**What a later change to the rule costs.** Nothing outside the `events` row holds a key today, and the nightly check computes every row again. So changing the rule now, or after production has rows, costs: new fixtures; the nights it takes to rewrite the stored keys at 200 a night, during which old and new keys are mixed; and a burst of `corrected` in the log that is not a fault. The point after which a change is no longer cheap is **the first time a key leaves the row**: the export of OSE-1617, or OW computing the same ids. From then on a changed rule is `v2`, with both versions to carry. A stored key does not say which version made it (the two columns hold the hash alone), so OSE-1617 has to carry the version beside the key when it exports one. What no rule change can repair is the text itself: an event typed "Eagles Hall, Blue Island" stays a different venue from one typed "Eagles Hall" until someone edits it.

**Open for the PO.** None of these stops the columns being stored: they are nullable and nothing reads them. The first one decides whether the venue key means anything across the two ways an event is created, so it comes before any real organizer uses the wizard. **OSE-1615's first acceptance line, "Same venue spelled two ways yields one `venue_canonical_id`", is met for spellings (case, apostrophes, "the", `&`, spacing) and is not met across the two create forms** (question 1). The migration itself has a date: OSE-1692 asks for it to land before the migration freeze of 2026-10-17 (`docs/runbooks/PRODUCTION-MIGRATION-PLAN.md`). A fix to the wizard is a template change and is not held by that freeze.

1. **The place field does two jobs, and the two forms ask for different things.** The key reads `location`. The wizard asks "Where is it?" with the example "Rock Island Public House, Blue Island" and has no address field; when a place is not found it says "Add the town or street so nearby searches show it" (`admin.html`, the wizard's place step). So the wizard teaches the organizer to put the city in the field the key reads. The dashboard form asks "Venue" and has a separate address field. The same venue entered through the two forms therefore gets two ids, which is the one thing OSE-1692's first test says must not happen. Options: (a) give the wizard a name field and an address field (a template change, its own PR; the place lookup already prefers the address); (b) change the rule to drop what follows the first comma (misses "Eagles Hall - Blue Island", and wrongly merges "Smith, Jones & Co." with "Smith"); (c) accept it. **Review recommendation, not a decision: (a), before the first real organizer uses the wizard; until then (c). Not (b).** On 2026-10-13 the PO had the columns merged with this question open; option (a) is written up as OSE-1717 and is not yet scheduled or decided. A wrong merge puts two venues' counts in one total. A split is not harmless either: each half can fall under the floor of 5 and be withheld, and more small cells are left beside the corridor totals. What (a) involves, from the review: six places in the wizard (the field, the create body, the edit list, the save, the review row and preview, the not-found note), new test ids and four specs; "Repeat this event" needs no change. What (a) does not do: an event already typed "name, city" keeps its split id until someone edits its place, and no rule change or nightly check can repair typed text.
2. **Accents.** Fold them ("Café" = "Cafe") or keep them apart, as now. This is not rare in the first market: "Taquería" and "Taqueria" get different ids, and a phone may add or drop the accent. Folding is cheap only until a key leaves the row. No recommendation was reached in review; the Data Scientist lens leans to folding.
3. **Coverage.** A key needs a map cell and a type. When the place lookup shipped, 3 of 174 staging events had a cell (`src/lib/event-place.ts`). Events with keys will lean toward venues Google can place. The nightly line reports how many of the events it read can have a venue key and an event key; any roll-up by key should state that coverage.
4. **Two events of one type at one venue on one night** share an event id, across brands too (two brands that each list the same night get the same id, by design; two different sessions get it as well). Two venues with the same generic name in one res-7 cell ("My house", "TBD") share a venue id.

Another repository that computes these keys must reproduce every row of the fixtures file.

### Decision 3: do the keys reach OW? (SETTLED, PO 2026-10-04)

**Leagues, chambers and the OW side must all be supported** by the spine keys. OW receives the keys, never person-level rows. Section 5 gives one recipe per buyer.

### Decision 4: do venue-grain keys cross the BigQuery boundary? (DECIDED, PO 2026-10-04: option A1)

Decision 3 says OW receives the keys on the pool it reads. That collides with three statements in force today:

- `OCR_ARCHITECTURE_oerAggregationBoundary.md` (OCR-docs, line 57): location is "corridor-level only (`corridor_id`)" for what OSE emits.
- `lib/export-geography.ts` (lines 10-11): "every row that crosses the D1 to BigQuery boundary is at corridor grain or coarser". `assertCorridorGrainRow` does not list `venue_canonical_id` as forbidden, so it would not stop the key, but those lines are the contract it enforces.
- OSE-1460 (PO, 2026-10-01), in `lib/shared-report-export.ts:291-292`: "The venue never leaves"; the aggregate exports carry `venue_id = 'corridor-aggregate'`.

ADR-010 (Proposed) section 3 assumes the opposite: that data meets in BigQuery keyed on the spine. So a Proposed ADR and an implemented boundary disagreed, and the PO settled it as set out below.

## 5. Roll-up recipes, one per buyer

Each recipe states the key it joins on and what the buyer may see. All of them stay inside the K=5 floor and the 90-day window rules of OSE-1460: a key never makes a withheld count visible.

**No back door by subtraction.** A roll-up returns the cells that clear the floor and the sum of those cells. It never returns an independent total, a count of events, or a share that would let a withheld cell be worked out by subtraction. If any cell is withheld the response says "some not shown", and does not say how many. The same applies to a league across its nights and a chamber across its venues.

### Chamber of commerce

- **Joins on:** `corridor_id` (the res-7 cell), and `venue_canonical_id` for venues that opted in.
- **May see, without any consent step:** floored counts per corridor and event type over the window, for **listed events only** (`is_published` and past the publish grace window, `listedSql()` in `lib/publish-grace.ts`). This is the grain the landing map and the corridor dashboard already publish.
- **May see only for a venue that opted in:** that venue's own floored counts. A venue is a separate tenant, so a chamber reading it per venue is a cross-tenant read and needs the venue owner's consent, recorded and audited in the same way as the league mapping below. A venue that only has draft or unlisted events never appears.
- **May not see:** anything below K=5, any per-event row for an event under the floor, any anonymous id, a venue that did not opt in.
- **Shape:** `GROUP BY corridor_id, uec_code` for everyone; `GROUP BY corridor_id, venue_canonical_id, uec_code` for opted-in venues. Each count is floored before it is summed. These counts are produced inside OSE (SharedReport and admin). No per-venue count reaches BigQuery (decision 4, A1).

### League

- **Joins on:** `brand_id` (the league as a tenant, with its events as children) and `uec_code`, over a date range. It does **not** join on `event_correlation_id`.
- **May see:** floored counts per night and for the season, across the venues where its teams played.
- **May not see:** another league's events at a shared venue; an attendee, or a team member, by identity.
- **Two cases.**
  - **A. The league owns its events** (the founding case: the league creates its Thursday nights and names the bar in `location`). Every event already carries the league's `brand_id`. No mapping is needed, and no consent step applies, because there is no other brand.
  - **B. The venues own the events** (each bar creates its own league night under its own brand). The league's `brand_id` is on none of them, so a mapping is needed: rows of (league brand, member event or venue brand, season start, season end). ADR-023 treats a venue and a league as separate private tenants, so a venue owner exists to consent. Whether a venue is a tenant in the code today is not verified; case A does not depend on it.
- **The mapping, where needed (case B), is held to these rules**, anonymity first:
  - **Identifiers of organisations and events only.** No person, team roster, player name, email, anonymous id or hash of one. A column outside the allowed set fails the gate OSE-1616 adds (its denylist covers `*_person*`, `email`, `ip`, `lat`, `lon`).
  - **Two-sided consent.** The league's owner proposes a member; the venue's brand owner accepts. Until both agree the row has no effect (the same rule as sponsor placements, ADR-019). Either side can remove it.
  - **Tenant isolation (invariant #9).** A league reads only events whose brand accepted the mapping, and only listed ones. A venue never sees another member's numbers.
  - **Audited writes.** Every add, accept and remove goes to `admin_audit_log` with the actor.
  - **The floor is applied per event before any sum**, and the no-subtraction rule above applies, so the mapping cannot be used to narrow a league down to a group under 5. A mapping that selects one night at one venue returns "not shown", not a small number.
  - **Held as tenant data, not a committed file.** Membership is a business fact with consent and an audit trail, so it belongs in a D1 table behind an admin route. A file in the repository is fine for test fixtures and for seeding the founding league, and nowhere else.

**Finding (resolved).** OSE-1617 words the league recipe as "by `event_correlation_id` across venues in a season". With the ADR-010 definition the venue is inside the hash, so a league night played at two venues yields two correlation ids. They cannot be joined by that key. `event_correlation_id` answers "is this the same event" (the same venue, type and night, entered once by OSE and once by OW). A season across venues is a tenant question, so it joins on `brand_id` plus `uec_code` plus dates. The PO agreed on 2026-10-04 and OSE-1617 was reworded to match.

### OW

- **Joins on:** all five keys, through the pool dataset OW reads (`oureventring_general`, per-environment names per OSE-1416). OW is to stamp the same `venue_canonical_id` and `event_correlation_id` at write time from the shared normalisation, so the halves agree by construction (ADR-010 section 1). That is design intent: no code in `ourWKRP` reads or writes either key today (searched 2026-10-04). There is no cross-database join. Under decision 4 (A1) OW joins events by key on `events_backup` and brings its own counts; OSE sends no per-event counts.
- **May see:** the keys on listed events, plus the floored, windowed aggregates that exist today (the `corridor_returns_export`, `corridor_density_baseline_export` and `event_series_export` shapes). No per-event counts leave OSE.
- **May not see:** `anon_id`, its hash, a per-person row, a count below K=5. Person-level participation on the OW side is the person's own opt-in declaration (the covenant in ADR-010 section 2), never inferred from a scan.

## 6. Dr of Security review

Claim to be checked: no key can single out a person.

- `venue_canonical_id` is derived from a venue name and an area cell. `event_correlation_id` adds an event type and a night. The inputs are about a place and an event, but the place field is free text: an organizer can type a home ("Sam's backyard", a street address). The id of such a place is then a stable id for a household, the same across brands and years (found in review, 2026-10-12). Nothing shows or exports the keys today; OSE-1617 must treat a venue key as it would treat the venue text, and must not publish a per-venue count next to one without the floor. An organizer also chooses the inputs, so an event can be given the key of another brand's venue or night by typing the same name in the same area: a reader must not treat a shared key as proof of a shared organizer. The keys are unkeyed hashes (they must agree across OSE and OW), so anyone who knows a venue and a night can compute the id and test whether an event exists. For a listed event that reveals nothing the public page does not say. For a draft, unlisted or archived event it would confirm something that is not public. So: the keys are stored for every event, but **exports and roll-ups carry them only for listed events** (OSE-1617 acceptance, added 2026-10-04), and no public surface shows them.
- A one-person event is the edge case: its id plus any exact count would identify that attendee's presence. The defence is the floor (`lib/count-floor.ts`), applied today by the SharedReport read, the dashboards, event stats, poster reach and the corridor map. This plan does not claim that every existing surface applies it; the rule is that any surface or export that shows a count next to a key must. A key never relaxes it (OSE-1617 acceptance), and exports also follow the no-subtraction rule of section 5.
- The hash input must not contain coordinates or res-9 cells (OSE-1615 security test).
- Keys are server-computed and never client-supplied (400 on a supplied value, as for `starts_at`).
