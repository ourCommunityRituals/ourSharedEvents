## A. Setup

**What was reviewed.** The change that adds two server-computed keys to the `events` row: `venue_canonical_id` and `event_correlation_id`. Migration 0104, the rule (`src/lib/spine-keys.ts`), the store and nightly check (`src/lib/spine-keys-store.ts`), the wiring in the event handlers, the place lookup and the scheduled handler, three test files, the published fixtures, four seed files, four Bruno requests, and the documents the change edits.

**Why it matters.** Every measure joins through `event_id`. These two keys are meant to give all of them a venue identity and an event identity that hold over time, and a sibling product (OW) is to compute the same ids on its own. A rule that is wrong, or keys that are wrong, are cheap to change only until a key leaves the row.

**In scope.** Correctness of the rule and of the stored keys; what leaves the Worker; the tests and whether they can fail; the path to staging; what the documents claim.

**Not in scope.** The export of the keys (OSE-1617), any reader of the keys, the wizard's templates, production (held closed; nothing here deploys or changes it).

**Classification.** A feature with a migration and a cross-repo data contract. The owner asked for three loops. The protocol's table gives 3 for a bug fix and 4 to 5 for a major upgrade; this sits between them. Three were run, as asked. Section C says what a fourth would be for.

**Team.** Product Owner, Lead Backend Architect, Lead FE Integration, Sr Design FE, Sr Automation QA, Sr SDET/SRE, DevOps Manager, Sr Data Scientist, Dr of Security. Each lens was a separate read-only agent given the diff and asked to find what is wrong. In loops 2 and 3 the two front-end lenses were one agent, because no template changed. The lenses ran in parallel inside a loop; the loops ran in order, and each loop's findings were fixed before the next began.

**How to read the evidence.** "Proven" means a command was run and its output read. "Source-read" means the finding comes from reading the code. The reviewing agents were told not to run the test suites (a full run was in progress in the same checkout), so their statements about tests are source-read unless they say otherwise. The suite results and the planted-fault results in section D were run by the builder.

## B. The loops

### Loop 1: surface pass

Reviewed: the first two commits (the rule and fixtures; the row, the nightly fill, the docs).

**Critical (the most dangerous assumption).** That "a stored key is absent or right, never wrong". It held only for writes made by the Worker's own code. Two seed files in the repo already changed a key input without clearing the keys, the nightly job only filled empty keys, and the test meant to guard the clear read source text in one folder.

**Conservative (the worst case).** An older Worker version running after the migration, a seed, or SQL run by hand leaves keys that describe a venue or night the row no longer has, and nothing ever repairs them. Separately, the nightly job re-read rows that can never have a key, oldest first, so enough of them would stop every other row getting a key.

**Recursive.** First loop, no earlier score.
